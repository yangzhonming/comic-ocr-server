# 阶段三：页序编号与本地图片采集

## 用法

1. 运行 `start_capture_server.bat`，服务监听 `127.0.0.1:8765`。
2. 加载或重新加载 `newplugin` 扩展，刷新漫画章节页。
3. 滚动页面检查可见漫画图左上角的序号。
4. 点击悬浮球，再点“开始采集并上传”。每章本次采集会生成新的 `chapter_id`。
5. 图片保存在 `captures/<chapter_id>/`；`000001.jpg` 表示漫画页序第 1 张。文件名完全使用前端传来的真实页序，与上传请求的到达顺序无关。`manifest.json` 记录 `image_id`、页序、尺寸、字节数和接收时间。

## 前端采集流程

- 仅扫描分类器给出的 `reader.root`。已识别图片作为列位置参考；同容器中宽度和水平中心与漫画列相符的图片占位元素也进入编号列表。
- 页序按图片几何纵坐标排序；同一纵坐标时按 DOM 顺序稳定排序。编号从 1 开始。可见图片上显示徽标，状态颜色用于区分等待、上传、成功与失败。
- 用户启动后，使用 `currentSrc` / `src`，再回退到 `data-src`、`data-original`、`srcset` 等懒加载来源。每张图通过独立 `Image` 加载，Canvas 以 JPEG 0.9 导出一次，再单独上传。
- 最大 3 个图片任务并发。请求包含 `file`、`chapter_id`、`page_index`、`image_id`、宽高。网络请求无须按漫画页序发送。
- 页序在已上传期间发生变化时停止后续采集并提示重新开始，防止新请求继续使用错位编号。已经保存的部分文件留在该次 `chapter_id` 目录，供人工检查。
- `image_id` 用于服务端重试去重；同一图片重复 POST 返回已保存文件。不同图片占用同一页号时返回 HTTP 409，不覆盖已有文件。

## 接收端

`../newplugin-server/capture_server.py` 是独立 FastAPI 接收服务，不加载旧后端 OCR 模型。`GET /health` 用于连接检查；`POST /capture` 接收 JPEG multipart 并使用 `page_index` 保存。所有写入在锁内检查重复页号并完成落盘，网络到达次序不会改变文件名。

接收服务监听 loopback 地址。项目 Manifest 中的 DNR 图片响应规则与旧版同类，用于让匿名跨域 `Image` 可以被 Canvas 读取；它对浏览器图片响应全局生效，真实站点上要观察是否影响图片加载或导出。

从公开网站请求本机服务时，较新的 Chrome 可能弹出本地网络访问许可提示；需要允许当前漫画站点访问本地接收器。Chrome 142 起正在推出该许可机制，浏览器版本和策略可能影响提示时机。

## 已知范围

- 方案面向 DOM `<img>` 长漫。Canvas、CSS 背景图、闭合 Shadow DOM、跨域 iframe 尚未采集。
- 页面滚动时才插入漫画前方图片会改变已有页序；采集器检测到已知图片重排后会停止后续上传。重新开始会创建新的采集目录。
- 当前限制每个上传图片 40 MiB，Canvas 内存峰值约为原图解码像素和 JPEG Blob 的合计；极端超长图片可能仍会导出失败。
- HTTP 接收次序以服务端完成文件读取并取得章节写入锁的顺序为准，不代表浏览器调用 `fetch` 的先后。
